# 01.5 - Kiln-Native Managed Agent Write Authority

## Status

Started on 2026-05-04. Slice 1 is complete as a documentation-only doctrine
slice. Slice 2 is complete as the first contract/admission implementation
slice. Slice 3 is complete as the runtime no-bypass enforcement boundary.

This roadmap is the bridge between `01` managed-agent invocation foundation and
later multi-child, scheduling, isolation, durable-workflow, and automation
roadmaps. It is named `01.5`, not `02`, because it completes the authority
model implied by managed invocations before Kiln expands the execution graph.

Do not open an ADR yet. This roadmap must first turn the Slice 0.5 research,
the canonical `01` decisions, and Kiln's control-plane doctrine into a
contract-first implementation plan.

## Decision Frame

The next capability is write authority for managed invocations.

This must be solved at the Kiln contract boundary, not inside one provider or
one harness. Direct API providers, OAuth-backed providers, wrapper providers,
CLI harnesses, local harnesses, cloud worktrees, and future remote execution
surfaces must all pass through the same authority model.

The first proof may use the adapter with the clearest evidence, but the
contract cannot be OpenCode-specific, Claude-specific, Codex-specific,
Hermes-specific, OpenClaw-specific, or tied to any provider-native vocabulary.

## Dependency From 01

`01` is closed as the managed-agent invocation foundation. `01.5` inherits
these proven primitives:

- `ManagedAgentInvocationRequest`
- `ManagedAgentAdmissionDecision`
- `ManagedAgentInvocationRecord`
- `ManagedAgentAdapterDescriptor`
- `RuntimeManagedAgentInvocationService`
- `ManagedCliHarnessAdapter` as one deterministic read-only proof path
- canonical `agent_invocation_*` events with structured
  `managedInvocationEvidence`
- `foundation-readonly-plan` as the first admitted profile
- governed context and memory admission through Kiln-owned policy
- secret-free credential route evidence
- replayable transcript, usage, diagnostics, timeout, cancellation, cleanup,
  and result-handoff evidence

These are the substrate. `01.5` must not reopen the foundation design unless a
write-authority gap proves the foundation contract incomplete.

## Goal

Define and implement Kiln-owned write authority for managed child invocations.

Every child write must be explicit, bounded, attributable, replayable,
cancellable, approval-aware, and reconstructable from canonical evidence.

The parent agent may request child work. The provider or harness may have
native write behavior. Only Kiln admits the effective write authority.

## Thesis

Kiln owns write authority.

Child agents do not inherit parent filesystem scope, memory scope, tool scope,
credential scope, or artifact mutation rights. A child can read, propose, or
apply changes only through an admitted authority profile and a bounded scope.

Provider-native write behavior is adapter capability metadata. It is not the
source of truth for whether a child invocation may mutate Kiln-governed state.

## Required Capabilities

- Cross-provider write authority contracts that apply equally to direct
  providers and harness-backed providers.
- Explicit authority profiles for read-only, propose-only, and approved-write
  execution.
- Scope envelopes for workspace paths, memory records, artifacts, resources,
  generated files, command execution, and future cloud/worktree sandboxes.
- Admission decisions that fail closed when requested write scope is missing,
  ambiguous, wider than allowed, or unsupported by the adapter.
- Write proposals that preserve intent, target, diff or operation summary,
  evidence links, risk metadata, and parent/child lineage.
- Approval decisions that are separate from provider execution and replayable
  through canonical events.
- Runtime enforcement that prevents direct adapter execution from bypassing the
  admitted authority profile.
- Memory mutation integration where child memory writes remain proposals unless
  an explicit memory-write authority has been admitted.
- Cleanup, rollback, and denial evidence for failed, cancelled, timed-out, or
  rejected writes.
- Operator projection through GUI, CLI, TUI, SDK, IDE, and remote surfaces from
  the same canonical evidence.

## Non-Goals

- Do not implement unbounded workspace write access.
- Do not grant implicit parent permissions to child invocations.
- Do not let provider-native agents apply writes outside Kiln admission.
- Do not make OpenCode, Claude Code, Codex, Hermes, OpenClaw, or another
  provider the base authority model.
- Do not add fan-out/fan-in, DAG workflows, scheduler policy, recurring
  automations, nested teams, or cloud worktree orchestration in this roadmap.
- Do not treat memory mutation as a generic file write. Memory has its own
  governed authority and lifecycle policy.
- Do not add hidden extension slices. If this roadmap cannot close in six
  slices, the remaining work starts a later roadmap.

## Authority Boundary

Write authority follows one boundary:

```text
parent turn or operator surface
  -> managed invocation request with requested authority
  -> Kiln admission policy and scope reduction
  -> child invocation with admitted authority profile
  -> write proposal or approved write attempt
  -> canonical write evidence, approval evidence, and session replay
  -> shared projection to operator surfaces
```

The child execution surface never decides its own final authority. It can only
advertise capabilities and return evidence.

## Canonical Vocabulary

Use Kiln-native names in core contracts:

| Term | Meaning |
| --- | --- |
| `ManagedAgentWriteAuthority` | The admitted write authority granted to a child invocation. |
| `ManagedAgentWriteScope` | The bounded targets a child may propose or mutate. |
| `ManagedAgentWriteProposal` | A child-produced mutation request that has not yet been approved or applied. |
| `ManagedAgentWriteDecision` | Kiln's approval, denial, or reduction decision for a proposed or requested write. |
| `ManagedAgentWriteAttempt` | A runtime attempt to apply an admitted write. |
| `ManagedAgentWriteEvidence` | Replayable evidence for proposal, decision, attempt, result, rollback, denial, or cleanup. |
| `ManagedAgentWriteProjection` | Surface-readable state derived from canonical events, not provider-local state. |

Provider terms such as patch, diff, edit, apply, PR, worktree, task write,
tool-use result, file operation, or memory save remain adapter metadata until
translated into this vocabulary.

## Authority Profiles

`01.5` starts with these profiles:

| Profile | Meaning | Allowed outcome |
| --- | --- | --- |
| `foundation-readonly-plan` | Existing `01` proof profile. | No writes, no memory mutations. |
| `foundation-propose-writes` | Child may inspect admitted context and return bounded write proposals. | Proposals and evidence only. |
| `foundation-apply-approved-writes` | Child may apply writes only after Kiln approval and scope admission. | Approved write attempts with replayable evidence. |
| `foundation-memory-write-proposals` | Child may propose memory mutations through governed memory contracts. | Memory proposals routed to memory authority, not direct durable writes. |

The names are deliberately conservative. Broader authority profiles require a
later roadmap or ADR.

## Scope Model

Write scope must be explicit and reducible:

- workspace path allowlist with normalized paths and denied path evidence
- memory scope with layer, tenant/project/session lineage, operation, and
  provenance rules
- artifact/resource scope with target IDs, retention policy, and redaction
  expectations
- command/tool scope with allowed tools, denied tools, and execution mode
- provider capability scope describing whether an adapter can propose writes,
  apply approved writes, isolate writes, rollback, or report diffs
- approval scope describing who or what can approve, whether approval is
  automatic or human-held, and which evidence must exist first

No authority profile may depend on a provider's implicit working directory,
native config file, inherited shell, provider memory, or untracked state.

## Event And Replay Requirements

Write authority must extend canonical session evidence without creating a
provider-local state namespace.

Required lifecycle evidence:

- write authority requested
- write authority admitted, reduced, or denied
- write proposal created
- write proposal approved, denied, or superseded
- write attempt started
- write attempt completed, failed, cancelled, timed out, rolled back, or left
  cleanup-pending
- memory write proposal routed to governed memory authority
- projection state reconstructed after session reload

Existing coarse invocation events may carry structured write evidence first.
A new event family is allowed only if reconstruction from the existing family
becomes ambiguous.

### Slice 1: Write Authority Doctrine And Vocabulary

Status: completed on 2026-05-04.

Define the doctrine before implementation:

- child writes are never inherited from the parent
- write authority is a Kiln admission result
- provider-native write capability is descriptor metadata
- proposal, decision, attempt, and evidence are separate concepts
- memory writes and workspace writes are separate authority domains
- denied or reduced authority is a first-class replayable state
- approval can be human, policy-driven, or unavailable, but it is never hidden

Exit criteria:

- official vocabulary is documented in this roadmap: met
- invariants are specific enough to write failing contract tests: met
- direct providers and harness providers are both covered by the same boundary:
  met
- no provider-native term becomes a core contract name: met

Deliverable:

- completed in this roadmap section. Slice 2 begins by writing failing core
  tests.

### Slice 2: Core Contracts And Admission Policy

Status: completed on 2026-05-04.

Implemented in Slice 2:

- added provider-neutral write authority contracts for scope, approval,
  proposals, decisions, attempts, evidence, adapter write capabilities, and
  authority profiles
- added `foundation-propose-writes`, `foundation-apply-approved-writes`, and
  `foundation-memory-write-proposals` to managed invocation admission profiles
- extended `ManagedAgentAuthorityProfile` with optional `writeAuthority`
  without making existing read-only invocations implicitly writable
- extended adapter descriptors with explicit write capability metadata
- extended admission decisions to carry admitted write authority evidence
- kept `foundation-readonly-plan` fail-closed when any write authority is
  requested
- denied write profiles when descriptor proposal/apply/memory/cleanup/scope
  capabilities are missing
- denied approved-write requests without write tooling, writable workspace, and
  approval evidence requirements

Add contract tests first for:

- `ManagedAgentWriteAuthority`
- `ManagedAgentWriteScope`
- `ManagedAgentWriteProposal`
- `ManagedAgentWriteDecision`
- `ManagedAgentWriteAttempt`
- `ManagedAgentWriteEvidence`
- write capability fields on `ManagedAgentAdapterDescriptor`
- authority fields on `ManagedAgentInvocationRequest`
- fail-closed write admission decisions

Admission must deny or reduce requests when:

- no authority profile is provided for requested writes
- requested write scope is wider than policy allows
- an adapter lacks required write proposal or approved-write capabilities
- memory mutation is requested without memory authority
- path scope is ambiguous, relative in an unsafe way, outside the allowlist, or
  provider-normalized differently than Kiln
- credential, tool, or command scope would expand beyond the parent-approved
  boundary

Exit criteria:

- core contract tests fail before implementation and pass after implementation:
  met
- no existing read-only invocation request becomes implicitly writable: met
- `foundation-readonly-plan` remains write-denied by default: met

### Slice 3: Runtime Enforcement Boundary

Status: completed on 2026-05-04.

Implemented in Slice 3:

- added runtime no-bypass tests for forged admitted decisions that omit write
  authority
- rejected direct `invokeAdmitted` execution when the adapter descriptor no
  longer satisfies the write capabilities required by the request
- required direct runtime admissions to match the current core admission
  decision, not merely carry an `admitted` status
- required write-profile runtime invocations to carry matching request and
  admission write authority
- rejected adapters that return records with authority broader than the
  admitted request
- kept read-only runtime invocations unable to return write authority or memory
  write proposals

Runtime must enforce authority after core admission:

- adapters execute writes only through an admitted decision
- direct adapter execution without admitted write authority fails closed
- provider-native patch or file-operation output is captured as proposal
  evidence unless approved-write authority exists
- approved write attempts are bounded to the admitted scope
- cancellation and timeout preserve partial write, cleanup, and rollback state
- denial evidence is appended before returning control to the parent

Exit criteria:

- runtime tests prove no-bypass behavior: met
- fake direct-provider and fake harness adapters both exercise the same
  authority boundary: partially met with the shared runtime adapter interface;
  direct-provider fixture remains for a later adapter-specific proof
- adapter descriptors cannot self-authorize writes: met

### Slice 4: Session Events, Replay, And Projection

Status: pending.

Write evidence must be reconstructable from canonical events.

Projection must support:

- requested, admitted, reduced, and denied write authority
- proposal list with current status
- approval decisions and decision actor/policy evidence
- write attempts and terminal states
- cleanup, rollback, timeout, and unknown evidence
- memory proposal routing state
- reload equivalence between live and persisted sessions

Exit criteria:

- gateway/operator presentation reads canonical write evidence
- GUI/TUI/SDK consumers do not need provider-specific write logic
- raw diffs or provider transcripts stay behind resource/artifact pointers when
  large, redacted, truncated, or external

### Slice 5: Memory And Artifact Write Integration

Status: pending.

Child writes that target Kiln memory or artifacts must use existing governed
subsystems instead of generic filesystem authority.

Required behavior:

- child memory writes become memory mutation proposals unless explicit memory
  write authority is admitted
- memory proposals carry parent session, parent turn, child invocation, child
  session, provenance, layer, scope, and lifecycle evidence
- artifact writes carry target identity, retention, redaction, and provenance
  metadata
- denied, superseded, approved, and applied states are replayable
- lifecycle policy can later evaluate child-produced memory without losing
  attribution

Exit criteria:

- tests prove child memory mutation cannot bypass `MemoryMutationService`
- artifact write evidence is linked, not copied into noisy inline payloads
- result handoff distinguishes workspace, memory, and artifact outcomes

### Slice 6: First Write-Authority Proof

Status: pending.

Prove one provider or harness path after Slices 1-5 establish the contracts,
tests, runtime boundary, session evidence, and memory/artifact integration.

Selection rule:

- choose the adapter that can provide the clearest proposal, approval, write
  attempt, transcript, cleanup, and replay evidence with the least hidden
  provider behavior
- do not choose the adapter because it is already the `01` proof path
- do not choose the adapter because its native vocabulary matches Kiln

Acceptable proof:

- deterministic fake provider or harness session
- no live external credentials
- no network call
- bounded workspace fixture
- proposal-only path first, approved-write path second if the boundary is
  already proven

Exit criteria:

- one admitted write-authority invocation produces replayable proposal,
  decision, attempt, and terminal evidence
- read-only invocations still cannot write
- direct providers and harness providers remain contract-compatible
- full targeted tests and typecheck pass
