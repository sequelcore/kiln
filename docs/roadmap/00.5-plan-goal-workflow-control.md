# 00.5 - Plan/Goal Workflow Control

## Status

Active planned roadmap.

This roadmap defines Kiln's durable workflow substrate for planning, goal
execution, governed delegation, effective authority, model intelligence policy,
and evidence-gated closeout.

This is the canonical roadmap track for current workflow control work. It must
not become a parallel governance-ML roadmap, a prompt-engineering guide, a GUI
local state feature, or a compatibility layer for pre-canonical workflow shapes.

## Completion Discipline

Roadmap progress is tracked by closed slices, not by scattered primitives.

A slice is complete only when all of these are true:

- every deliverable in the slice exists in the canonical runtime/contracts/docs
- every verification bullet has focused tests or a documented manual evidence
  record
- canonical docs describe the implemented behavior without roadmap-only claims
- reload/replay/reconnect behavior is covered when the slice claims durability
- cross-surface behavior is covered when the slice claims cross-surface support
- remaining work is empty, or explicitly moved to a later slice without blocking
  the current slice contract

Partial implementation does not unlock the next slice. If a later slice already
has partial primitives, new work must still return to the earliest incomplete
slice unless the change is required to preserve existing behavior or unblock that
earlier slice.

## Objective

Make Kiln's default non-trivial workflow:

```text
intent intake
  -> constitution and instruction-profile alignment
  -> structured specification
  -> clarification gate
  -> governed plan
  -> plan/spec consistency analysis
  -> operator approval
  -> effective turn authority admission
  -> durable goal run
  -> work-item execution
  -> model/provider and reasoning-effort policy
  -> managed-agent delegation when appropriate
  -> verification and review gates
  -> evidence-gated closeout
  -> canonical documentation update
```

Plan mode reduces ambiguity before mutation.

Goal mode executes an approved plan through durable, inspectable work items.

Model intelligence policy determines which admitted model/provider route should
be used for work, with what reasoning effort, and why.

Effective turn authority determines what a turn is actually allowed to do. A
surface may request authority, but only runtime admission grants effective
authority.

Parent agents remain accountable for integration and closeout. Managed children
provide bounded evidence for specific work.

## Product Thesis

Kiln should not depend on magic prompts such as:

```text
be 100% confident
continue until done
use the best model
do not make mistakes
```

Those phrases express operator intent, but they are not architecture.

Kiln's advantage is turning that intent into explicit runtime contracts:

- structured specifications instead of ambiguous feature prose
- structured plans instead of prose-only planning
- work items instead of transient checklists
- effective turn authority instead of surface-local permission claims
- model intelligence policy instead of manual per-prompt model tuning
- routing rationale instead of hidden provider selection
- managed child invocations instead of ambient delegation
- evidence gates instead of confidence claims
- replayable session events instead of hidden model memory
- cross-surface projections instead of GUI-only workflow state
- plan/spec consistency checks instead of hoping a model notices drift
- dataset-ready traces instead of premature fine-tuning infrastructure

Kiln governs. Models work inside Kiln.

## Design Commitments

### 1. Runtime authority is canonical

No surface owns authority.

GUI, TUI, CLI, SDK, MCP, native harness shims, and managed children may request
authority. Runtime admits effective authority.

### 2. Model/provider is routing state, not session identity

A single Kiln session may use multiple providers/models across turns. Provider
selection must not fragment session truth.

### 3. Auto model selection is policy, not magic

"Auto by Kiln" means:

```text
Kiln chooses an admitted provider/model route based on policy, evidence,
authority, task suitability, cost, health, and reasoning-effort support.
```

It does not mean an LLM freely chooses tools, providers, or authority.

### 4. Manual override remains explicit

Manual provider/model overrides are allowed only as explicit operator intent.
They must record source, reason when available, and effective route.

Manual override cannot bypass:

- route health
- provider availability
- authority admission
- skill admission
- cost policy
- safety policy
- reasoning-effort support
- tenant policy

### 5. ML and fine-tuning are deferred

This roadmap creates model-use governance and dataset-ready traces.

It does not implement:

- a Kiln-native governance model
- ML-based routing
- fine-tuning
- governance dataset generation
- AllostaticLoad as a first-class metric
- full GovernanceDecision as a monolithic schema

Those become valid only after the relevant runtime decisions are real,
observable, testable, and evaluable.

### 6. Extract abstractions only after consumers exist

Do not create `KilnStateSnapshot`, `GovernanceDecision`, `OperationalMode`, or
`AllostaticLoad` until the implementation has real consumers that need them.

Use small, bounded inputs first:

- `EffectiveTurnAuthorityInput`
- `ModelRoutingPolicyInput`
- `ToolAuthorityInput`
- `WorkItemMaterializationInput`
- `GoalRunTransitionInput`

Consolidate only when duplication appears across real consumers.

## Target Contract

### Constitution and Specification

Kiln should separate durable doctrine from per-feature specification:

- global and project instruction profiles define constitution-level rules:
  engineering standards, testing posture, architecture constraints, UX
  standards, safety posture, and verification expectations
- a feature specification defines what should be built and why, without
  prematurely selecting technology or implementation shape
- clarification records reduce ambiguity before planning
- consistency analysis checks constitution, specification, plan, and work items
  before implementation

Specification artifacts may be exported as markdown for humans and native
harness shims, but runtime authority must come from canonical
specification/plan/work-item events and resources.

### Plan Mode

Plan mode is a bounded read-only phase.

It may:

- inspect
- ask clarifying questions
- assess work governance
- identify affected surfaces
- identify risks
- submit a structured plan

It may not:

- mutate files
- execute hidden implementation
- widen authority
- create durable work truth outside canonical events
- bypass runtime tool admission

`submit_plan` should become a structured contract with:

- objective
- non-goals
- operator decisions required
- assumptions
- affected surfaces
- risk classification
- work governance recommendation
- proposed work items
- expected evidence
- verification gates
- managed-agent delegation candidates
- approval boundaries
- rollback or recovery notes
- residual risks
- source specification id
- clarification record ids
- constitution/instruction profile hash

Plans that lack required fields for their risk level fail validation.

### Goal Mode

Goal mode is not "keep looping."

It is an execution controller for an approved plan.

A goal run contains:

- goal id
- originating plan id
- objective
- status
- work item ids
- current milestone or phase
- budget and timeout policy
- owner session
- allowed authority envelope
- route policy
- evidence requirements
- interruption and resume state
- closeout result

Goal mode executes through canonical work items and managed-agent invocations.
It must be resumable from runtime/session evidence, not from fragile chat
history.

### Work Items

Work items are canonical execution units.

Each work item records:

- source plan id
- goal run id when applicable
- dependency order
- route and agent recommendations
- authority profile
- context mode
- expected evidence
- verification requirements
- recommended model intelligence tier
- recommended reasoning effort
- assigned execution surface
- completion attempt history
- residual-risk statement

### Effective Turn Authority

Every admitted turn must have effective authority.

A requested authority is operator intent. An effective authority is runtime
truth.

Effective authority is derived by:

```text
effectiveAuthority =
  min(
    requestedAuthority,
    sessionPolicy,
    tenantPolicy,
    routePolicy,
    parentAuthority,
    planApproval,
    goalEnvelope,
    workItemAuthority
  )
```

Effective authority must include:

- execution mode
- approval mode
- filesystem policy
- network policy
- requested authority
- admitted authority
- source policy
- completeness
- reason
- sandbox projection

No builtin tool may execute without explicit effective sandbox.

Mutating tools must be filtered before provider invocation when effective
filesystem policy is read-only.

### Model Intelligence and Reasoning Effort

Model selection has separate dimensions:

- provider/model route
- task suitability
- reasoning effort
- cost policy
- latency policy
- route health
- provider availability
- authority eligibility
- skill eligibility
- tenant policy
- operator override
- ranking evidence

Reasoning effort is normalized as:

```text
minimal | low | medium | high | xhigh
```

Effort selection remains bounded by provider discovery.

Kiln must not invent unsupported reasoning effort.

If a work item requires stronger effort than the selected route supports,
routing must choose another eligible route or fail closed with a diagnostic.

Ranked suitability is evidence, not truth. Static profiles, operator overrides,
community reports, and creator rankings may be used as advisory evidence only
when source, task family, rank, reason, scope, and expiry are recorded.

Durable route preference must be reinforced by live proof, internal evals, or
project-specific outcome history.

A top-ranked route still cannot bypass route health, provider availability,
authority admission, cost policy, or reasoning-effort support.

### Dataset-Ready Governance Traces

This roadmap should produce structured traces that can become datasets later.

It should not produce a training dataset yet.

Each relevant turn should be able to emit enough evidence to reconstruct:

- requested authority
- effective authority
- route selected
- routing rationale
- provider/model used
- reasoning effort used
- tool requests
- tool authority decisions
- approval requests and outcomes
- safety signals
- cost and latency
- work item and goal state
- evidence submitted
- residual risk
- operator override
- closeout result

These traces are for audit, debugging, evals, and future dataset generation.

They must be redaction-aware, tenant-aware, and privacy-policy-aware.
