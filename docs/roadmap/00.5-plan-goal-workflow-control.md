# 00.5 - Plan/Goal Workflow Control

## Status

Active planned roadmap.

This roadmap defines Kiln's durable workflow substrate for planning, goal
execution, and governed delegation. It must be implemented as a first-class
control-plane capability, not as prompt engineering, compatibility behavior, or
surface-local state.

## Objective

Make Kiln's default non-trivial workflow:

```text
intent intake
  -> constitution and instruction-profile alignment
  -> structured specification
  -> clarification gate
  -> governed plan
  -> plan/spec consistency analysis
  -> operator approval
  -> durable goal run
  -> work-item execution
  -> managed-agent delegation when appropriate
  -> verification and review gates
  -> evidence-gated closeout
```

Plan mode reduces ambiguity before mutation. Goal mode executes an approved
plan through durable, inspectable work items. Parent agents remain accountable
for integration and closeout; managed children provide bounded evidence for
specific work.

## Product Thesis

Kiln should not depend on magic prompts such as "be 100% confident" or
"continue until done." Those phrases are useful symptoms of what operators
want, but they are not architecture.

Kiln's advantage is that it can turn that intent into explicit runtime
contracts:

- structured plans instead of prose-only planning
- work items instead of transient checklists
- managed child invocations instead of ambient delegation
- model intelligence and reasoning-effort selection as governed routing
  evidence instead of manual per-prompt tuning
- evidence gates instead of confidence claims
- replayable session events instead of hidden agent memory
- cross-surface projections instead of GUI-only workflow state
- effective turn authority instead of surface-local permission claims
- specification and plan consistency checks instead of hoping a model notices
  drift

This is the bridge between planning discipline and long-running agent work.

## Research Basis

The direction is supported by current product behavior, community workflows,
and agent-planning research:

- Anthropic Claude Code guidance recommends separating exploration, planning,
  implementation, and commit; using plan mode for uncertain or multi-file work;
  and delegating investigation or verification to subagents to preserve parent
  context.
- OpenAI's Codex guidance recommends using Ask Mode to produce implementation
  plans for large changes before switching to execution mode.
- OpenCode's plan mode disables mutation tools by default and allows planning
  without changing the codebase.
- GitHub Spec Kit demonstrates the market direction from "AI writes code" to
  "AI executes a structured specification." Its constitution, specify,
  clarify, plan, tasks, analyze, and implement workflow is strong evidence
  that high-quality AI development needs explicit artifacts, ambiguity
  reduction, quality gates, dependency-ordered tasks, and cross-artifact
  consistency checks.
- OpenAI's Agents guidance describes manager-style orchestration where a
  central agent coordinates specialized agents through explicit tool calls.
- Community long-running-agent workflows converge on upfront clarification,
  durable state files, milestone decomposition, parallel workers in isolated
  workspaces, review loops, progress logs, and strict verification before
  closeout.
- Planning research categorizes effective LLM-agent planning around task
  decomposition, plan selection, external tools, reflection, and memory.
- Multi-agent software-engineering research such as MetaGPT shows that encoded
  operating procedures and specialist verification reduce inconsistent
  chained-agent behavior.
- Recent multi-agent topology research shows that prompts and communication
  topology both matter; Kiln should therefore model workflow topology as
  governed state, not only as instructions.

Kiln's implementation must absorb these lessons into canonical runtime
contracts while preserving Sequel standards: no redundant systems, no dead
workflow files, no legacy compatibility paths, no hidden state, no surface-local
authority, and no unverifiable completion claims.

## Existing Foundations

This roadmap builds on completed Kiln doctrine and implementation:

- `docs/guides/plan-mode.md`
  defines planning as read-only diagnosis and design, with `submit_plan` as the
  planning output tool.
- `docs/architecture/work-governance.md`
  defines orchestration preference, direct-execution envelopes, workflow
  profiles, work items, expected evidence, and evidence-gated closeout.
- `docs/architecture/managed-agents.md`
  defines managed child invocation authority, route identity, evidence,
  handoff, and replay.
- `docs/architecture/agent-context.md`
  defines operator identity, instruction profiles, agent profiles, skills, and
  child context modes.
- GUI and TUI already project governed work items from canonical session state.
- Runtime tool surfaces already expose `work_governance.assess`,
  `work_item.update`, `work_item.list`, `work_item.complete`, `submit_plan`,
  and `managed_agent.invoke`.

The next step is to make these pieces one coherent workflow lifecycle.

## Non-Goals

- Do not clone Codex `/goal` as a blind continuation loop.
- Do not clone Claude Plan Mode as a surface feature.
- Do not clone GitHub Spec Kit's file layout or slash-command surface as Kiln's
  authority model.
- Do not create a second task database beside canonical session events.
- Do not keep durable workflow truth in markdown scratch files.
- Do not let GUI, TUI, CLI, SDK, MCP, or native harness shims invent their own
  workflow lifecycle.
- Do not let any surface claim or imply a sandbox/tool authority that was not
  admitted by the runtime for the current turn.
- Do not make every task use plan mode or goal mode.
- Do not require managed-agent delegation for trivial local work.
- Do not treat child completion, model confidence, or checklist text as task
  completion.
- Do not add backwards compatibility for any pre-canonical workflow shape.

## Target Contract

### Constitution and Specification

Kiln should separate durable doctrine from per-feature specification:

- global and project instruction profiles define constitution-level rules:
  engineering standards, testing posture, architecture constraints, UX
  standards, and verification expectations
- a feature specification defines what should be built and why, without
  prematurely selecting technology or implementation shape
- clarification records reduce ambiguity before planning
- consistency analysis checks constitution, specification, plan, and work items
  before implementation

Specification artifacts may be exported as markdown for humans and native
harness shims, but runtime authority should come from canonical
specification/plan/work-item events and resources.

### Plan Mode

Plan mode is a bounded read-only phase. It may inspect, ask clarifying
questions, assess work governance, and submit a structured plan. It may not
perform implementation or hidden execution.

`submit_plan` should become a structured contract with:

- objective
- non-goals
- operator decisions required
- assumptions
- affected surfaces
- risk classification
- work governance recommendation
- proposed work items
- expected evidence
- verification gates
- managed-agent delegation candidates
- approval boundaries
- rollback or recovery notes
- residual risks
- source specification id
- clarification record ids
- constitution/instruction profile hash

Plans that lack required fields for their risk level should fail validation.

### Goal Mode

Goal mode is not "keep looping." It is an execution controller for an approved
plan.

A goal run should contain:

- goal id
- originating plan id
- objective
- status
- work item ids
- current milestone or phase
- budget and timeout policy
- owner session
- allowed authority envelope
- route policy
- evidence requirements
- interruption and resume state
- closeout result

Goal mode executes through canonical work items and managed-agent invocations.
It must be resumable from runtime/session evidence, not from fragile chat
history alone.

### Work Items

Work items are the execution units. They remain the canonical task state for
cross-surface projection.

Each work item should record:

- source plan id
- goal run id when applicable
- dependency order
- route and agent recommendations
- authority profile
- context mode
- expected evidence
- verification requirements
- recommended model intelligence tier and reasoning effort
- assigned execution surface
- completion attempt history
- residual-risk statement

### Model Intelligence and Reasoning Effort

Model selection has two separate dimensions:

- model/task suitability: whether a provider/model is preferred, capable, or
  limited for a task such as architecture review, frontend design, research,
  mechanical edits, backend coding, or test writing
- reasoning effort: the provider-supported intelligence level for the selected
  model, normalized as `minimal`, `low`, `medium`, `high`, or `xhigh`
- ranked field performance: ordered evidence that a provider/model is the best
  currently admitted choice for a task family such as frontend/design,
  backend, code review, raw reasoning, research, or mechanical edits

Kiln already exposes model task suitability and supported reasoning efforts as
runtime discovery and route evidence. Workflow control must use that evidence
when materializing work items and invoking managed children. A child route
should not receive `xhigh` just because the parent is uncertain, and a
mechanical edit should not burn a high-reasoning route when a configured fast
route satisfies the evidence gate.

Effort selection must remain bounded by provider discovery. If a route does not
advertise supported reasoning efforts, Kiln must not invent one. If a work item
requires a stronger effort than the selected model supports, routing should
choose another eligible route or fail closed with a diagnostic.

Ranked field performance must be evidence-backed. Community reports, creator
rankings, and operator taste are useful discovery signals, but they are not
canonical truth. Kiln should admit them as `operator-override` or
`static-profile` evidence only when the record states source, task, rank,
reason, and scope. Durable routing preference should be reinforced by live
proof, internal evals, or project-specific outcome history. A route ranked
first for frontend design still cannot bypass route health, provider
availability, authority admission, skill admission, cost policy, or reasoning
effort support.

### Managed Children

Managed children execute bounded slices. Parent agents decide, route, integrate,
and close.

When a work item is delegated, `managed_agent.invoke` must receive:

- `workItemId`
- `roleIntent`
- `expectedEvidence`
- `requiredResultFields`
- `doneCriteria`
- `residualRiskRequired`
- provider/model and reasoning-effort recommendation when policy selects one
- route or agent recommendation when known

The returned handoff must be validated before the parent can complete the work
item.

## Slices

### Slice 1 - Constitution and Specification Intake

Define the structured intake layer that precedes planning.

Deliverables:

- canonical specification artifact schema
- specification resource projection
- instruction-profile/constitution snapshot attached to each specification
- clarification record schema with question, answer, affected section, and
  rationale
- validation taxonomy for ambiguity, missing non-goals, vague success criteria,
  undefined actors, unclear data lifecycle, UX edge cases, security/privacy
  posture, external dependencies, and completion signals

Verification:

- specification artifacts can be reconstructed from session events
- clarification answers update the specification without duplicating or
  contradicting previous statements
- planning fails closed when required specification fields remain unresolved
- generated repo/harness shims can reference the specification without becoming
  the source of truth

### Slice 2 - Structured Plan Contract

Convert `submit_plan` from text-first output into a typed plan artifact.

Deliverables:

- shared schema for plan submission
- runtime validation by risk/workflow profile
- canonical `plan_submitted` event with structured fields
- resource projection for plan artifacts
- CLI/GUI/TUI text fallback that renders the same structured content
- linkage to source specification, clarification records, and instruction
  profile snapshot

Verification:

- plan-mode tests prove mutating tools stay unavailable
- invalid plans fail closed
- valid plans replay from session events without provider-native state
- unresolved specification ambiguity blocks plan approval for governed profiles

### Slice 3 - Plan/Spec Analysis Gate

Add a read-only analysis gate before approval and before implementation.

Deliverables:

- analyzer that compares specification, plan, generated work items, expected
  evidence, and active instruction profiles
- findings model for duplication, ambiguity, underspecification, constitution
  conflict, coverage gap, task/order inconsistency, and terminology drift
- severity levels with fail-closed behavior for critical conflicts
- resource projection for analysis reports
- stable finding ids so revisions can close or supersede findings without
  losing history

Verification:

- critical constitution conflicts block approval
- requirements without executable work-item coverage are reported
- implementation cannot start while blocking findings remain open
- analysis is read-only and cross-surface

### Slice 4 - Plan Approval and Transition

Make approval an explicit transition from plan to execution.

Deliverables:

- approval event tied to immutable plan hash
- execution transition that references the approved plan id
- rejection/revision loop without creating duplicate plans
- cross-surface projection for approve, reject, revise, and execute

Verification:

- changed plan content invalidates stale approval
- execution cannot start from unapproved or malformed plan
- GUI/TUI/CLI consume the same events

### Slice 5 - Effective Turn Authority and Permission Admission

Make permission for each turn a runtime contract instead of prompt text,
surface-local state, or model self-reporting.

The failure mode this slice prevents: a surface displays or prompts "read-only"
while the effective per-call tool surface still exposes mutating tools such as
`write`, `edit`, `patch`, or shell execution. That drift is a workflow-control
failure, not a UI wording issue.

Deliverables:

- canonical `EffectiveTurnAuthority` domain model with execution mode, approval
  mode, filesystem policy, network policy, requested authority, admitted
  authority, source policy, completeness, and reason
- `requestedAuthority` field on operator turn submission for GUI, TUI, CLI, SDK,
  and managed-agent invocation surfaces
- admission rule:
  `effectiveAuthority = min(requestedAuthority, sessionPolicy, routePolicy,
  parentAuthority, planApproval, goalEnvelope, workItemAuthority)`
- tool allowlist and tool definitions derived only from effective authority
- required sandbox projection for every builtin tool execution; no builtin tool
  may execute without an explicit effective sandbox
- mutating tools filtered before provider invocation whenever the effective
  filesystem policy is read-only
- approval-required result and canonical approval events for authority elevation
  when policy allows `on-request`
- cross-surface authority status projection for welcome, turn-start, done,
  transcript, session events, and resource snapshots
- mutation audit that records a security violation if file changes are observed
  outside the admitted authority
- managed-child authority inheritance where children can receive equal or
  narrower authority than the parent, never broader implicit authority
- composer controls for per-turn permission in GUI and TUI, with the same
  requested-authority contract available to CLI and SDK callers

Verification:

- GUI, TUI, CLI, SDK, and managed-agent tests prove read-only turns do not expose
  `write`, `edit`, `patch`, or destructive shell tools
- fake-provider integration tests prove a model-requested write fails closed
  under read-only effective authority
- approval-mode tests prove mutating tools return approval-required before
  execution and run only after approval is recorded
- executor tests prove builtin tools receive an explicit sandbox on every call
- authority-status tests prove displayed status matches the per-call config used
  for the turn
- post-turn audit tests prove file changes under read-only are recorded as
  violations and cannot be projected as normal successful completion
- child-invocation tests prove subagents inherit or narrow parent/work-item
  authority and cannot widen it through route selection

### Slice 6 - Goal Run Domain Model

Introduce the goal-run aggregate as the durable execution controller.

Deliverables:

- goal-run domain types and validators
- `goal.created`, `goal.updated`, `goal.completed`, `goal.failed`,
  `goal.cancelled` canonical session events
- `kiln://session/goals` and `kiln://session/goals/{id}` resources
- no separate storage model outside session/event/resource contracts

Verification:

- goal runs can be reconstructed from events
- cancellation and failure states are terminal and auditable
- goal events do not duplicate work-item state

### Slice 7 - Plan-to-Work-Item Materialization

Turn an approved plan into ordered governed work items.

Deliverables:

- deterministic materializer from plan artifact to work items
- dependency validation
- deduplication by stable ids
- work-governance profile mapping
- route and agent recommendation projection
- model task-suitability and reasoning-effort recommendation per work item

Verification:

- repeated materialization is idempotent
- circular dependencies fail closed
- work items retain the plan and goal provenance
- generated work items explain why a route/effort was recommended

### Slice 8 - Model Intelligence Policy

Make model intelligence and reasoning effort part of governed orchestration
rather than a manual composer-only setting.

Deliverables:

- workflow policy that maps workflow profile, risk level, task suitability, and
  evidence requirements to a requested reasoning effort
- admission check that the selected provider/model advertises the requested
  effort before execution
- managed invocation propagation of policy-selected `providerRoute.reasoningEffort`
- operator override support that records override reason and source
- route diagnostics when no available model satisfies task suitability and
  effort requirements
- ranked suitability policy that orders eligible provider/model routes per task
  family using static profiles, operator overrides, live proof, internal evals,
  cost, latency, and recent route health
- evaluation evidence import shape for model-field rankings, including source,
  task, rank, sample size or confidence when known, and expiry/review policy

Verification:

- architecture/security/high-risk analysis can request stronger effort when
  supported
- mechanical edits default to lower effort when evidence requirements permit
- unsupported effort requests fail closed before execution
- managed child records include effective provider, model, and reasoning effort
- direct-provider and CLI-harness routes use the same policy decision
- rankings affect only eligible routes and cannot make unavailable or
  unauthorized providers admissible
- stale or unsupported ranking evidence expires or degrades to advisory
  diagnostics instead of silently driving route selection

### Slice 9 - Goal Execution Loop

Build the controller that advances work items without becoming a hidden agent
loop.

Deliverables:

- select next ready work item
- decide direct execution versus managed delegation through
  `work_governance.assess`
- invoke managed children when policy requires delegation
- require evidence before item completion
- update goal state after each item transition
- pause when required operator input, credentials, or approval is missing

Verification:

- no work item advances without required evidence
- parent remains accountable for integration closeout
- failed child handoff blocks or retries according to policy
- long-running execution resumes from recorded state

### Slice 10 - Cross-Surface Operator UX

Expose the workflow lifecycle consistently in GUI, TUI, CLI, and SDK.

Deliverables:

- GUI plan review and goal run view
- TUI compact goal/work-item projection
- per-turn permission control in GUI and TUI composers that submits
  `requestedAuthority` without granting authority locally
- CLI commands for listing, inspecting, approving, cancelling, and resuming
  goals
- CLI and SDK request shape for `requestedAuthority`
- SDK/resource access to plan, goal, and work-item snapshots
- presentation-intent support where needed, without creating custom state

Verification:

- all surfaces render the same canonical state
- no surface owns workflow truth
- reload/reconnect preserves plan, goal, and work-item state
- displayed permission state matches runtime-admitted effective authority

### Slice 11 - Verification and Review Gates

Make evidence closeout stricter for goal-driven work.

Deliverables:

- per-profile evidence matrix
- reviewer/adversarial review gate for risky profiles
- browser QA gate for UI profiles
- build/type/test gate recording
- residual-risk requirement before goal completion

Verification:

- a goal cannot complete with missing evidence
- skipped checks require explicit residual-risk evidence
- review findings remain linked to the work item or goal they block

### Slice 12 - Native Harness and Export Projection

Project the same workflow into external harnesses without letting projected
files become authoritative.

Deliverables:

- export of current specification, plan, work-item, and instruction-profile
  snapshots for native harness consumption
- generated shims for Codex, Claude Code, OpenCode, Copilot/Cursor-style
  command or skill surfaces where supported
- projection manifest with hash, source ids, and generated file list
- drift diagnostics when projected markdown differs from canonical state

Verification:

- deleting generated harness files does not delete canonical workflow state
- regenerated files are deterministic for the same source artifacts
- projected commands cannot bypass runtime authority when used inside Kiln
- standalone harness usage sees the same workflow doctrine as a readable shim

### Slice 13 - Cleanup and Canonical Documentation

Absorb implementation results into stable docs and remove roadmap residue.

Deliverables:

- update `docs/guides/plan-mode.md`
- update `docs/architecture/work-governance.md`
- add or update canonical specification/goal workflow docs
- add or update a canonical goal/workflow guide
- update global-config guidance for workflow policy
- remove obsolete plan files or temporary workflow docs

Verification:

- no near-duplicate workflow doctrine remains
- roadmap file lists no completed implementation detail after closure
- generated repo shims project only canonical guidance

## Configuration

Global and project config should control policy, not duplicate workflow logic.

Expected future config shape:

```yaml
workflow:
  specification:
    requireClarificationFor:
      - architecture
      - security
      - ui
      - runtime
      - managed-agents
      - config
      - multi-file
      - long-running
  plan:
    requireStructuredPlanFor:
      - architecture
      - security
      - ui
      - runtime
      - managed-agents
      - config
      - multi-file
      - long-running
    allowDirectExecutionForSmallFixes: true
  goals:
    enabled: true
    maxActive: 1
    requirePlanApproval: true
    requireEvidenceCloseout: true
    pauseOnMissingCredentials: true
  authority:
    defaultTurnAuthority: read-only
    allowWorkspaceWriteRequest: true
    requireApprovalFor:
      - destructive-shell
      - dependency-install
      - delete
    blockMutationWhenReadOnly: true
    auditOutOfAuthorityMutation: true
  intelligence:
    defaultEffortByRisk:
      low: low
      medium: medium
      high: high
    taskEffort:
      architecture-review: high
      security: high
      frontend-design: medium
      mechanical-edit: low
    allowOperatorOverride: true
    rankings:
      enabled: true
      requireEvidenceSource: true
      staleAfterDays: 30
  analysis:
    blockOnCriticalFindings: true
    requireCoverageForApprovedPlans: true
```

This config should narrow or tune the canonical workflow. It must not let a
project define an incompatible lifecycle.

## Open Questions

1. Should goal runs be session-scoped only at first, or should they immediately
   support durable cross-session continuation from the local runtime store?
2. Should `submit_plan` create work items directly, or should materialization
   occur only after explicit approval?
3. What is the smallest useful GUI goal view: plan summary plus work-item list,
   or a full timeline from the first slice?
4. Which workflow profiles should require managed-agent delegation by default
   in the first implementation?
5. Should CLI expose `kiln goal start --from-plan <id>` immediately, or should
   GUI-driven approval be the first product path?
6. Should Kiln use the term "constitution" publicly, or keep it internal as
   instruction-profile governance to avoid duplicate concepts?
7. Should feature specifications be first-class session artifacts only, or also
   persisted under `.kiln/specs/` as human-editable projections?
8. Should reasoning effort be selected only by workflow profile and risk, or
   should evaluation history also adjust defaults over time?
9. Should community/model-market rankings be stored as first-class
   operator-override evidence, or imported only through explicit local eval
   runs?
10. Should per-turn authority default to read-only for all interactive surfaces,
    or should standalone CLI retain workspace-write when explicitly launched
    with a write-capable harness mode?
11. Should destructive shell authority be a separate turn-level authority, or
    should it always require per-command approval even inside workspace-write
    turns?

## Acceptance Criteria

This roadmap can close only when:

- plan mode emits structured, validated plan artifacts
- non-trivial plans are linked to a structured specification and clarification
  record
- blocking specification/plan/work-item analysis findings prevent execution
- approved plans materialize deterministic work items
- every turn records requested and effective authority, and all surfaces project
  the effective authority from the same runtime contract
- read-only authority prevents mutating tools from being exposed or executed
- managed child invocations cannot receive broader authority than their parent
  or work item envelope
- work items carry model/task suitability and reasoning-effort recommendations
  when execution is delegated or high-risk
- orchestration can rank eligible routes per task family without treating
  community reports or static profiles as proof
- goal runs execute and resume from canonical events/resources
- managed-agent delegation carries work-item evidence requirements
- managed child records include effective reasoning effort when one was
  selected or requested
- work-item completion fails closed without required evidence
- GUI, TUI, CLI, and SDK consume the same state
- canonical docs describe the workflow without relying on roadmap text
- no temporary markdown state, duplicate task store, or legacy compatibility
  path remains
