# 06.5 - End-To-End Harness Efficiency

Status: Research
Execution: Research - define the benchmark contract before optimizing any path.
Created: 2026-08-25

## Objective

Make Kiln's task latency and execution cost attributable from operator request
to terminal outcome, then admit only optimizations that materially improve the
measured bottleneck without weakening outcome, safety, authority, privacy,
replay, or cross-surface semantics.

Prompt caching is an input-prefill optimization owned by
[Roadmap 06](06-prompt-governance-plane.md). This track consumes its cache
evidence but measures the complete path: preparation, provider queue/prefill
and generation, transport, tools, retries, compaction, orchestration, startup,
and the number of model turns.

## Current Position

Kiln records provider token usage, logical request-cache regions, tool events,
effective prompt identity, benchmark scores, and local startup milestones.
Those signals are not yet one task-level latency account. There is no committed
paired live baseline showing whether provider prefill, output generation,
tools, transport, orchestration, retries, or startup dominates representative
Kiln work.

The evidence and source limitations live in
[Harness Cache And End-To-End Efficiency](../research/active/harness-efficiency.md).
That research establishes that cache-hit rate, prompt size, total cost, task
success, and end-to-end latency can rank the same harnesses differently. It
does not establish a current cross-harness winner or a Kiln bottleneck.

## Goals

- Produce one attributable task timeline over existing canonical request,
  provider, tool, retry, compaction, and terminal-outcome evidence.
- Define comparable cold, warm, post-TTL, and long-session fixtures before
  collecting promotion evidence.
- Report TTFT, provider completion, tool, orchestration, startup, and total wall
  time separately rather than collapsing them into one unexplained duration.
- Preserve task outcome, required content, safety, authority, privacy, and tool
  trajectory as hard gates ahead of speed or cost.
- Identify the smallest current owner that can remove each measured bottleneck.
- Allow a cross-harness comparison only when model, provider, task, tools,
  environment, versions, repetitions, and limitations are explicit.

## Ownership

This track owns the task-level efficiency benchmark, latency attribution,
comparability contract, bottleneck evidence, and optimization promotion gate.

Existing owners remain unchanged:

- Roadmap 06 owns prompt components, provider cache topology, and progressive
  disclosure.
- Core and Runtime own their canonical events and execution semantics.
- Provider adapters own transport and honest projection of supported controls.
- Tool implementations own tool-specific performance after the benchmark
  identifies them as a bottleneck.
- Roadmap 09 owns admission of Rust, WASM, N-API, or sidecar acceleration; this
  track can identify a hot path but cannot select a native implementation.
- Release operations own installable-package and exact-candidate evidence.

## Scope

- A versioned task fixture and execution-condition identity.
- Cold, warm, post-short-TTL, and long-session trial definitions.
- Task-level correlation of preparation, provider, tool, retry, compaction,
  orchestration, startup, and terminal-outcome evidence.
- TTFT, provider completion latency, tool queue/execution latency, total wall
  time, calls, turns, retries, compactions, input/output/cache tokens, and cost.
- p50, p95, sample count, failure and timeout rates, and uncertainty reporting.
- Baseline/candidate parity and regression gates.
- Optional cross-harness fixtures after the Kiln baseline is reproducible.

## Non-Goals

- No universal "fastest harness," "best performance," or code-quality claim.
- No use of cache-hit ratio, prompt size, output length, bundle size, or one
  synthetic task as a proxy for task outcome or total latency.
- No duplicate prompt-cache, provider-usage, tool-event, startup, or terminal
  outcome authority.
- No provider/model/price/TTL choice in doctrine.
- No benchmark-only execution path that differs from the real Runtime path.
- No optimization before bottleneck attribution.
- No Rust or other native implementation decision; Roadmap 09 remains the
  admission boundary.

## Complexity Disposition

Required invariant: every promoted efficiency change improves an attributable
real path while preserving execution semantics and governance gates.

The simplest considered design was to add total duration and cache-hit ratio to
Roadmap 06. It is insufficient because a provider cache hit explains neither
output decoding, tool latency, retries, extra turns, startup, nor terminal task
success, and it would make prompt governance own unrelated runtime performance.

This track adds one permanent concept: a versioned task-level efficiency result
that references existing event and configuration identities. It adds no second
provider timer, prompt manifest, tool event, or outcome store. Instrumentation
gaps are closed in the current owner and correlated by shared execution
identity. If that correlation cannot be achieved without duplicating truth,
the affected slice is rejected or redesigned.

The exported cost is benchmark maintenance across provider/model revisions and
supported platforms. That cost is justified only for representative fixtures
used by an actual optimization or release decision. Obsolete comparisons and
raw operator-specific payloads are not retained.

## Ordered Slices

### Slice 0 - Benchmark Contract

Status: Research.

Define the fixture, execution-condition, timing-region, result, and comparison
contracts. Reuse canonical execution, effective-prompt, provider-usage, tool,
retry, compaction, and terminal-outcome identities. Define clock source,
correlation, warm-up, timeout, failure, repetition, aggregation, and redaction
semantics before collecting release evidence.

Representative fixtures cover at least repository discovery, bounded editing,
tool-heavy work, malformed tool recovery, exact-date research, safety refusal,
and a long session that reaches compaction. Each fixture declares required
outcome, allowed tool surface, provider/model route, and whether the condition
is cold, immediately warm, post-short-TTL, or long-session.

Acceptance: a maintainer can reproduce one result from committed synthetic
fixtures and exact config/revision identity; the benchmark uses the production
Runtime path; timing regions do not overlap or double count without an explicit
relationship; unsupported provider timing remains unknown; and raw prompts,
secrets, credentials, and operator-specific paths are absent.

### Slice 1 - Kiln Baseline And Attribution

Status: Queued behind Slice 0 and the relevant live-test authority.

Run repeated trials on at least one admitted OpenAI-family route and one
Anthropic route. Report cold, warm, post-short-TTL, and long-session results,
including absolute cache read/write/uncached tokens from Roadmap 06. Attribute
total task time to provider queue/prefill when exposed, generation, transport,
tools, retries, compaction, orchestration, and startup without fabricating
unavailable segments.

Acceptance: the committed evaluation reports p50, p95, sample count, failures,
timeouts, outcome scores, cost, calls, turns, retries, compactions, and residual
unattributed time. It identifies a bounded bottleneck or records a no-action
result. One local run is never described as population or release evidence.

### Slice 2 - Bounded Optimization

Status: Blocked on Slice 1 bottleneck evidence.

Assign the measured bottleneck to its existing owner and compare the smallest
candidate against the exact baseline. Candidates may include request assembly,
provider transport, output limits that preserve required content, tool
implementation, parallel independent tool work, retry/compaction behavior, or
startup discovery. Prompt-prefix or progressive-disclosure candidates return
to Roadmap 06; native acceleration candidates must separately pass Roadmap 09.

Acceptance: the candidate materially clears a predeclared threshold on the
target region and total task outcome; p95 and failure rate do not materially
regress; outcome, safety, authority, privacy, required content, and tool
trajectory remain non-inferior; rollback is exact; and the result names any
complexity exported to configuration, packaging, operations, or another owner.

### Slice 3 - Optional Cross-Harness Comparison

Status: Deferred until Slice 1 is reproducible and an explicit product decision
needs external comparison.

Compare current Kiln, Pi, Claude Code, Codex, OpenCode, or Gemini CLI only when
the same provider/model, task, allowed tool capability, repository fixture,
machine class, repetitions, and terminal outcome can be made materially
comparable. Record exact harness revisions and unavoidable prompt/tool/runtime
differences. Report a metric vector, never one aggregate winner.

Acceptance: exclusions, failures, unavailable costs, vendor conflicts, and
non-equivalent capabilities remain visible; each quantitative claim is scoped
to the measured workload; and the result can honestly terminate with no
ranking or no promotion.

## Promotion Gates

- Baseline and candidate use the same production execution path and committed
  fixture identity.
- Provider, model, route, config, prompt manifest, tool surface, price evidence,
  machine class, harness revision, and repetition policy are recorded.
- TTFT, provider completion, tools, orchestration, and total wall time remain
  separate attributable regions.
- Absolute uncached input accompanies cache-hit rate.
- Task outcome, correctness, required content, safety, authority, privacy, and
  tool trajectory are non-inferior before latency or cost is considered.
- p50, p95, sample count, failures, timeouts, and uncertainty are visible.
- No aggregate gain hides a material route-, model-, platform-, or fixture-
  specific regression.
- The optimization has an existing owner, deletion/rollback path, and no
  duplicate state or benchmark-only behavior.
- Live credentials, quota, subscriptions, and provider charges require explicit
  operator authority.

## Verification

Contract and serialization tests; synthetic timeline-correlation fixtures;
missing/partial-provider-timing tests; timeout and failed-task accounting;
cache cold/warm/post-TTL fixtures from Roadmap 06; task-outcome and authority
regression suites; startup-profile compatibility; repeated live provider
evaluation when authorized; affected-package tests; workspace typecheck;
`docs:check`; and `git diff --check`.

Independent model review may challenge fixture coverage or interpretation but
does not verify timing, parity, or task outcome.

## Completion Criteria

Kiln can explain where representative task time and cost went; operators can
distinguish cache, provider, tool, orchestration, and startup effects; every
promoted optimization names its measured bottleneck and preserved invariants;
and no current decision relies on a social superlative or non-comparable
harness result. Stable contracts move to architecture, dated measurements move
to `docs/evaluations/`, and this track is then removed.
