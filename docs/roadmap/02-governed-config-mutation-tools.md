# Governed Config Mutation Tools

Status: Active
Opened: 2026-05-07

## Objective

Expose Kiln setup and configuration as governed native tools so agents can
inspect configuration, propose changes, and apply approved changes without
editing YAML or provider files directly.

This turns configuration into part of Kiln's control plane. Agents may help the
operator add skills, adjust agents, inspect routes, enable providers, update
defaults, or synchronize projections, but only through structured contracts,
schema validation, authority checks, explicit approval, and audit evidence.

## Scope

- Add read-only config inspection tools for effective config, providers, routes,
  agents, skills, permissions, memory authority, native projection status, and
  provider health.
- Add structured config-change proposal tools for bounded operations:
  - add or update a skill
  - add or update an agent profile
  - attach skills to an agent profile
  - change default provider or model
  - enable or disable a configured route
  - update managed-agent route selection defaults
  - request native projection sync
- Add approved config-apply tools that write only canonical Kiln config and
  then run the projection/sync pipeline through existing services.
- Emit canonical config mutation events with before/after summaries, affected
  files, authority, approval, validation diagnostics, and projection results.
- Make the same read/propose/apply contracts available to GUI, TUI, CLI,
  SDK/widget, and future operator surfaces.

## Non-Goals

- Do not expose generic file-edit access as configuration mutation.
- Do not let agents directly edit Claude Code, Codex, OpenCode, or other native
  harness files; those remain projections.
- Do not bypass schema validation, duplicate detection, route admission,
  permission evaluation, or operator approval.
- Do not allow config mutation tools in planning-only or read-only child
  contexts unless the request is explicitly read/propose-only.
- Do not add backwards-compatibility migration layers without real consumers.
- Do not make third-party skills or agent packs installable in this slice.

## Tool Shape

Initial tools should be small and explicit:

```ts
kiln_config.read({
  view: "effective" | "providers" | "routes" | "agents" | "skills" |
    "permissions" | "memory" | "projections" | "health"
})

kiln_config.propose_change({
  operation: "skill.upsert" | "agent.upsert" | "agent.attach_skills" |
    "routing.set_default" | "route.set_enabled" | "projection.sync",
  payload: { ... }
})

kiln_config.apply_change({
  proposalId: "...",
  approvalId: "..."
})
```

`propose_change` returns a structured proposal, not a patch string:

- operation
- normalized payload
- affected canonical config paths
- native projection effects
- authority impact
- validation diagnostics
- preview diff
- rollback hint

`apply_change` may only apply a validated proposal that still matches current
config state. If config changed since the proposal was produced, it must fail
closed and require a fresh proposal.

## Architecture Rules

- Canonical Kiln config remains the only write target.
- Native harness files are regenerated by projection services, not patched by
  config tools.
- Proposal validation must use the same schemas and loaders used by CLI/runtime
  config resolution.
- Apply must be idempotent when the same approved desired state already exists.
- Every mutation must emit audit evidence and be visible in operator Activity.
- Managed children inherit only the config tools admitted by their authority
  profile; generic read-only children get `kiln_config.read` at most.
- Config mutation authority is separate from filesystem write authority.

## First Implementation Slices

1. Extract canonical config read/projection status services so CLI commands and
   future tools share one implementation.
2. Add `kiln_config.read` for read-only effective config and projection status.
3. Add proposal domain types and validators for skill and agent profile changes.
4. Add `kiln_config.propose_change` for `skill.upsert`,
   `agent.upsert`, and `agent.attach_skills`.
5. Add approval-gated `kiln_config.apply_change` for those first operations.
6. Wire apply to existing sync/projection services and emit config mutation
   events.
7. Render proposals and mutation events in GUI Activity, TUI, CLI output, and
   SDK/widget event streams.

## Acceptance Criteria

- An operator can ask an agent to add a skill or attach it to an agent profile,
  and the agent can produce a validated proposal without direct file editing.
- Applying the proposal requires explicit approval and writes only canonical
  Kiln config.
- Native Claude/Codex/OpenCode files are updated only through projection/sync.
- Unknown operations, invalid names, duplicate aliases, unsafe authority
  expansion, stale proposals, and missing approvals fail closed.
- GUI, TUI, CLI, and SDK/widget observe the same proposal/apply events.
- Tests cover read views, proposal validation, stale proposal rejection,
  approval-gated apply, projection invocation, and audit event emission.

## Deferred

- Third-party skill and agent pack install/import.
- Team/cloud config distribution and review workflows.
- Rich GUI config editor.
- Policy packs and organization-level config governance.
