# OpenCode Go Catalog and Roster Reassessment

Date: 2026-08-01

> Write-authority conclusions in this catalog screen are superseded by
> `27-write-and-render-route-admission-2026.md`, which contains the isolated
> backend and rendered-frontend evidence and final route closeout.

## Decision

The local OpenCode Go configuration is not catalog-obsolete: every configured
model still exists in the live 17-model catalog. It is nevertheless obsolete
as an operating roster in two material ways:

1. At audit start, `deepseek-v4-flash` was assigned to private-repository
   scouting and writes, while OpenCode Go says this route may be used for model
   training and provides no retention agreement. The 2026-08-01 closeout
   removed it from routing, suitability, gateway admission, managed routes, and
   affected agent profiles.
2. The roster predated stronger or safer economic challengers. `hy3`,
   `mimo-v2.5`, `mimo-v2.5-pro`, and `minimax-m3` were screened locally; none
   earned an active route from catalog presence alone.

No public leaderboard justified replacing the routes immediately. This
closeout therefore added an evidence-gated, read-only roster profile over a
portable synthetic fixture and ran the current catalog candidates through it.
The one immediate policy conclusion independent of model quality remains the
privacy quarantine above.

## Scope and Evidence

This reassessment covers the catalog returned by the authenticated local
OpenCode Go account on 2026-08-01 and the current official Go product page.
The catalog, prices, quotas, retention declarations, and terms are volatile.
They must be rediscovered before a later promotion.

OpenCode Zen is a separate provider identity. Its current privacy page also
states that data sent to DeepSeek V4 Flash Free during the free period may be
used to improve the model. The stale Zen Flash write example was removed during
this closeout; no Go conclusion is transferred automatically to Zen or vice
versa.

Evidence is ordered as follows:

1. live provider discovery and replayable Kiln route evidence;
2. official OpenCode Go and model-lab documentation;
3. independent benchmarks with visible methodology;
4. practitioner reports, used as workload hypotheses;
5. community reports, used only to identify tests and failure modes.

Artificial Analysis scores below are a current broad-intelligence prior, not a
Kiln ranking. Scores from different index versions are not comparable. A route
is the complete tuple of provider, exact model, harness, mode, authority,
context policy, and task profile.

## Independent Capability Priors

The current Artificial Analysis broad-intelligence results cluster the Go
catalog approximately as follows: Kimi K3 57, Grok 4.5 54, GLM 5.2 51,
Qwen3.7 Max 46, MiniMax M3 and DeepSeek V4 Pro 44, Kimi K2.7 Code and MiMo
V2.5 Pro 42, Hy3 41, Qwen3.7 Plus 39, MiniMax M2.7 38, and MiMo V2.5 37.
These values are not a universal ordering and do not measure Kiln's authority,
route reliability, privacy boundary, source fidelity, or repository-specific
quality.

The official model evidence supplies useful hypotheses:

- GLM 5.2 emphasizes long-horizon coding, tool use, and a 1M context window.
  Its vendor benchmarks are unusually strong, while independent reports also
  note high token consumption.
- MiniMax M3 combines a 1M window with native multimodality and adaptive
  reasoning. This makes it more relevant than M2.7 for Kiln's visual/frontend
  evaluation, not automatically a better implementer.
- MiMo V2.5 is a low-cost 1M omnimodal model; V2.5 Pro is a larger text model
  aimed at complex software and long tool trajectories. Hosted Go capabilities
  still require live proof.
- Hy3's official evaluation highlights frontend, CI/CD, and data/storage work,
  with explicit attention to tool-format stability across harnesses. That maps
  directly to a Flash-replacement experiment.
- Qwen3.7 Max is a strong, fast long-context text prior. Qwen3.7 Plus is the
  cheaper multimodal hypothesis. Qwen3.8 Max Preview is newer in Alibaba's
  product family but is not offered by the live OpenCode Go catalog and cannot
  be configured here.
- Grok 4.5 has strong independent coding-agent evidence, but its Go quota and
  retention make it a poor fit for private Sequel work already covered by
  first-party frontier routes.

## Audit of the Local Configuration

At audit start, `~/.kiln/config.yaml` contained seven OpenCode models:
`kimi-k3`, `kimi-k2.7-code`, `deepseek-v4-pro`, `qwen3.7-max`, `glm-5.2`,
`minimax-m3`, and `deepseek-v4-flash`. All seven remain discoverable.

The audit found:

- Flash was `preferred` for `mechanical-edit`, had read-only and approved-write
  routes, and was admitted to the managed route set despite the incompatible
  data declaration. Closeout removed those paths. `scout` and `fast-coder` now
  use already-admitted Codex Terra routes; the generic `opencode` worker uses
  the existing GLM 5.2 approved-write route.
- At audit start, MiniMax M3 was configured and rated `capable` for mechanical
  edits but had no virtual model, managed route, or agent consumer. The
  closeout removes that unused route and suitability entry.
- Only GLM 5.2 retains write-capable routes after the task-specific closeout.
  Kimi K2.7, Qwen3.7 Max, DeepSeek V4 Pro, and Codex Terra write routes were
  removed rather than retained provisionally.
- Kimi K3 has the correct read-only boundary, but its quota and measured route
  failures make it an escalation/challenger rather than a default.
- The config has no privacy/retention admission field. Today this safety fact
  exists outside route selection, so configuration review must fail closed
  until Kiln gains an executable provider-data-policy boundary.

Historical route health also limits the current assignments. GLM 5.2 has an
older success but its latest recorded outcome is a provider `500`. Qwen3.7 Max
has three recorded requests, no recorded success, and a latest provider `500`.
Neither historical record proves a permanent model defect. The fresh roster
run now proves GLM's current route at 20/20 read-only cases; Qwen has only one
clean four-case smoke and must not be described as equivalently repeatable. No
local artifact exposes the remaining five-hour, weekly, or monthly Go quota.

The repository has two additional drift surfaces:

- the global config guide and sanitized task-aware example still recommended
  older Kimi, GLM, Qwen, MiniMax, and Go Flash routes; this closeout updated
  those examples and removed the unsafe Go Flash recommendation;
- the static Core capability/suitability registry contains several older
  OpenCode identities and lacks several current exact IDs. Direct Go admission
  uses live discovery, so this does not resurrect Flash, but the registry must
  not be treated as current pricing, capability, or readiness authority.

## Lean Candidate Roster

The target is not to configure all 17 models. The smallest defensible candidate
pool for profile-v3 comparison is:

| Task family | Incumbent | Challengers | Promotion question |
| --- | --- | --- | --- |
| Backend, services, tests, architecture | GLM 5.2 | MiMo V2.5 Pro; DeepSeek V4 Pro | Does either challenger improve terminal reliability, behavioral correctness, latency, and token cost on real Sequel fixtures? |
| Scout and mechanical work | Codex Luna | Hy3; MiMo V2.5 | Which privacy-safe route wins on inventory recall, patch accuracy, latency, and terminal success? |
| Frontend implementation | Unassigned | Kimi K2.7 Code; Kimi K3; Codex through a leased benchmark route | Which route first passes rendered interaction, accessibility, screenshot, and diff-quality scorers repeatedly? |
| Visual critique and multimodal intake | Kimi K3 read-only | MiniMax M3; Qwen3.7 Plus; MiMo V2.5 | Does the exact Go route accept the modality and produce actionable, grounded handoffs at usable reliability? |
| Source-grounded research | Qwen3.7 Max | GLM 5.2; frontier read-only route | Which route has the best claim coverage, citation entailment, source quality, and contradiction detection? |

Candidates that lose their specific comparison should be removed rather than
kept as generic fallbacks. The expected eventual OpenCode roster is three to
five distinct specialists, not a catalog mirror.

## Required Profile-v3 Evaluation

Each comparison must preserve:

- exact provider, model, model-returned identity, harness and adapter version;
- task profile, authority, tools, context policy, reasoning/mode and timeout;
- provider response id, terminal state, error class, retries, usage and latency;
- repository commit, synthetic portable fixtures, dataset hash and scorer
  version;
- at least five repeated runs per task, with confidence intervals where the
  sample supports them;
- execution-integrity scoring before any quality credit;
- task-specific external scorers: tests and diff integrity for code, rendered
  and accessibility evidence for frontend, and citation entailment for
  research;
- explicit data-policy eligibility before repository context is disclosed.

The first queue is:

1. remove Flash from the private-code candidate set;
2. Hy3 versus MiMo V2.5 versus Luna on read-only scout and isolated mechanical
   fixtures;
3. MiniMax M3 versus Kimi K2.7 and Codex on the managed frontend profile;
4. MiMo V2.5 Pro versus GLM 5.2 and DeepSeek V4 Pro on backend/service work;
5. Qwen3.7 Max versus GLM 5.2 on source-grounded research;
6. delete every losing or consumerless route after evidence is preserved.

## Configuration Closeout

### Reproducible local screening result

Kiln now has `kiln-model-roster` version 2, a read-only screening profile with
four synthetic tasks: repository impact mapping, backend contract diagnosis,
frontend/accessibility review, and primary-versus-secondary source
reconciliation. The runner:

- resolves a repository-relative fixture and rejects traversal, absolute paths,
  symlinks, and non-file entries;
- runs directly in the synthetic root without projecting the real Kiln
  repository or creating an isolated worktree from `HEAD`;
- uses a sanitized model-facing context with no operator identity, project
  instruction profiles, project hooks, work-governance tools, or live project
  web/interactive configuration;
- binds the baseline config hash and every result to fixture hash
  `sha256:ead3f82e0919d09b168fe4f558ac5158bd50704b756b22590b98c016123d288b`;
- re-resolves and rehashes the fixture after every session, invalidating the
  run if its persistent bytes or symlink topology changed;
- scores evidence from model output rather than dataset-declared milestones;
- requires exact fixture citations, a grounded read/search trajectory, terminal
  success, and exact provider/model identity before quality credit.

The initial profile-v1 `k=1` screening results were used only to select the
finalists. They share one live operator context and are therefore comparable
diagnostics, but they do not have profile v2's sanitized portability boundary:

| --- | ---: | ---: | --- |
| `kimi-k2.7-code` | 4/4 | 48.8 s | Advance to repeated screening. |
| `glm-5.2` | 4/4 | 80.6 s | Advance to repeated screening. |
| `mimo-v2.5` | 4/4 | 102.7 s | Dominated on this profile; retain only as a future task-specific challenger. |
| `minimax-m3` | 4/4 | 116.4 s | Dominated and consumerless; remove from general routing. |
| `qwen3.7-max` | 4/4 | 140.7 s | One research smoke is insufficient to beat GLM's repeated evidence. |

| `mimo-v2.5-pro` | 3/4 | 134.2 s | Did not advance. |

Only the quality/latency Pareto frontier advanced. Independent review then
identified live-context projection and missing post-run fixture verification;
profile v2 closed both gaps and invalidated reuse of the earlier repeated
results. The finalists were rerun from scratch under v2:

| --- | ---: | ---: | ---: | ---: | --- |
| `glm-5.2` | 20/20 | 4/4 | 1.00 | 11.8 s | `sha256:e318939ade7da38f610a12ce85774b51482a344bb59febd4ae34a1addbc8cfc3` |
| `kimi-k2.7-code` | 19/20 | 3/4 | 0.75 | 9.0 s | `sha256:3d2e3ac87d902bff4b890ac5aae364e287c42d237c7af90485675a0615ab682a` |

The profile threshold was fixed before the repeated runs: at least three of
four tasks must pass all five repetitions. Both routes met that threshold, but
GLM was the unique 20/20 route. Kimi was 5/5 on backend, frontend, and research
and 4/5 on scouting, while also posting the lower median latency. Kiln therefore
keeps GLM as the OpenCode default and Kimi as the fast frontend specialist and
bounded general challenger. This screening does not authorize writes:
frontend, backend, or mechanical write assignments still require isolated
patch, test, typecheck, and diff-integrity profiles.

The immediate operator-config quarantine was applied atomically:

- removed Flash suitability, general routing, virtual model, managed admission,
  read-only route, approved-write route, and agent references;
- reassigned affected agents only to already-admitted routes;
- parsed the canonical config successfully and confirmed through `kiln status`
  that no Flash managed route remains;
- updated repository examples that previously recommended the Go Flash route.
- removed the consumerless MiniMax M3 general fallback after it lost the
  evidence/latency screen;
- made GLM 5.2 the preferred OpenCode research route and downgraded Qwen3.7 Max
  to a challenger until it has repeated evidence.

The remaining follow-up is deliberately evidence-gated:

- add no replacement write route until task-specific write/test results exist;
- keep Hy3 and MiMo V2.5 outside active routing unless a later task-specific
  fixture demonstrates a non-overlapping advantage;
- encode provider data-use and retention eligibility in executable config so
  future routing cannot depend on a prose warning.

Promoting a replacement before the evaluation and data-policy contract exist
would repeat the same hidden-policy failure under a new model name.

## Residual Risks

- OpenCode Go is an aggregator; model identity, hosted capabilities, quotas,
  pricing, availability, and data terms can change independently.
- Zero-day retention is a provider declaration, not an independently audited
  guarantee in this research.
- External benchmarks use different prompts, tools, reasoning modes, and
  infrastructure from Kiln.
- The roster result measures read-only analysis over one small synthetic
  fixture. It does not establish patch quality, visual capability, multimodal
  transport, security behavior, or performance on a real private repository.
- The current runtime cannot enforce the provider privacy eligibility found by
  this audit.
- Static model capability/suitability evidence still trails the dynamic Go
  catalog. Replacing it requires a separate tested contract change, not guessed
  capabilities copied from model cards.
